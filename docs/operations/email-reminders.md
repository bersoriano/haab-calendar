# Booking email reminders

Apply `20261118230550_booking_email_reminders.sql` before deploying application code. Set `REMINDER_LINK_SECRET` to a stable random secret of at least 32 characters, alongside existing `RESEND_API_KEY`, `BOOKING_EMAIL_FROM`, `NEXT_PUBLIC_SITE_URL`, and `CRON_SECRET`. Keep reminder secret across deployments: changing it invalidates management links sent in earlier reminders.

The booking trigger writes one primary reminder (24 hours before) and an optional second reminder into `booking_email_reminders` in the booking transaction. Business settings and service opt-outs refresh pending rows. Cancellation and rescheduling cancel old pending rows. Appointment times use the business IANA timezone; full-day bookings use 09:00 local as the reminder anchor. A reminder whose configured lead time has already passed is not sent late at booking creation.

`.github/workflows/scheduled-workers.yml` calls `/api/cron/booking-reminders` every five minutes with `Authorization: Bearer $CRON_SECRET`. The endpoint claims up to 50 due rows per call under `FOR UPDATE SKIP LOCKED` and a two-minute lease. Worker reloads booking, business, service, and reminder state before sending. Resend receives an idempotency key based on the reminder row ID. HTTP failures retry with bounded backoff, up to eight attempts, then enter `dead_letter`; the worker logs a safe error code and row ID. Missing or deleted bookings cannot be sent. Check `booking_email_reminders` for `failed` or `dead_letter` rows when investigating delivery. GitHub scheduling can run late; rows remain due until processed, but reminders are skipped once appointment starts.

Database flow tests run with `npm run test:db -- test/db/booking-email-reminders.test.ts` after local migration. Against a local Haab database at the prior migration, set `REMINDER_TEST_DB_URL` and `REMINDER_TEST_INLINE_MIGRATION=1`; each test applies migration inside a transaction and rolls it back.

Reminder mail contains service, local date and time, duration, business name, optional business message, and signed self-service link. Booking language is saved when a client confirms; older bookings use the business language. It selects no client notes. The signed link uses a server HMAC and remains valid alongside original booking links. It requires no client account and stores no raw management token in the database.
